2. Product Definition
Personal Operating System is a structured behavioral analysis and self-understanding system.

It helps users transform experiences into structured, testable, version-controlled knowledge about how they operate.

The application is based on a workbook originally called:

Personal Operating System Workbook

The digital product is not intended to reproduce workbook pages as electronic forms.

Instead, it turns the concepts behind those worksheets into connected data, workflows, evidence, experiments, and system changes.

The central product question is:

What setting am I running?

rather than:

What's wrong with me?

3. Product Thesis
Most reflection applications optimize for recording experiences.

Personal OS optimizes for learning from them.

Traditional model:

Experience → Write → Save

Personal OS model:

Experience → Debug → Observe → Discover → Link Evidence → Test → Learn → Update → Release

The long-term accumulated value of the product is not:

"Everything I have written."

It is:

"The model I have built of how I operate."

4. Product Identity
Personal OS should feel like:

5. Core Product Loop
The fundamental Personal OS lifecycle is:

OBSERVE ↓ DEBUG ↓ DISCOVER ↓ LINK EVIDENCE ↓ FORM HYPOTHESIS ↓ EXPERIMENT ↓ REVIEW RESULT ↓ UPDATE SYSTEM ↓ RELEASE VERSION ↓ UPDATE OPERATING MANUAL

This is the primary product loop.

Every significant feature should either:

help the user move through this loop, or
make the knowledge generated by the loop more useful.
6. Core Domain Concepts
Personal OS uses the following major domain concepts.

6.1 User
An authenticated person using Personal OS.

6.2 Workspace
The private container for a user's Personal Operating System.

All behavioral data belongs to a Workspace.

The architecture supports workspace membership, although Personal OS initially operates primarily as a private single-user system.

6.3 Debug Session
A structured record of a situation the user wants to investigate.

Typical fields include:

Situation
Trigger
Thoughts
Emotions
Behavior
Outcome
Analysis Lens
Occurrence Time
A Debug Session is an input into the system.

It should not automatically be treated as a conclusion.

6.4 Observation
A structured observation derived from an experience or analysis.

Observations provide source material for Evidence.

The distinction between a Debug Session and Observation is important:

Debug Session records what happened.

Observation records something learned or noticed from what happened.

6.5 System Component
A structured piece of knowledge about how the user operates.

System Components are among the most important objects in Personal OS.

Supported component types include:

Setting
Rule
Assumption
Need
Protective Strategy
Strength
Warning Sign
Recovery Method
Resource Requirement
Operating Condition
Components evolve as evidence accumulates.

7. Settings
A Setting represents a recurring configuration or tendency in how the user operates.

Example:

Setting:

Need for Clarity

Category:

Decision Making

Status:

Confirmed

Description:

Performance improves when expectations, constraints, and ownership are clear.

Possible costs:

Excessive information seeking when complete clarity is unavailable.

Evidence:

DBG-0012
DBG-0027
DBG-0041
EXP-0006
A Setting should become more useful as additional evidence accumulates.

8. Rules
Rules represent internal operating instructions.

Examples:

"Always finish what you start."

"Do not act until you understand the entire problem."

"If there is uncertainty, gather more information."

Rules can be:

discovered
tested
adopted
modified
deprecated
retired
A Rule may belong to or relate to one or more Settings.

9. Assumptions
Assumptions represent propositions the system appears to be treating as true.

Example:

"If I act without complete information, I will probably make a bad decision."

Assumptions are intended to be testable.

They should not be treated as facts simply because they were discovered.

10. Needs and Protective Strategies
The Protective Lens introduces additional concepts.

A Need represents something that may be important to the user in a situation.

A Protective Strategy represents a response that may be attempting to preserve or provide something important.

Example:

Need:

Predictability

Protective Strategy:

Delay action until uncertainty decreases.

The application should support reflection without claiming psychological diagnosis.

11. Evidence
Evidence is a first-class relationship.

A System Component should not simply exist because a user typed it once.

It should be possible to answer:

Why do I think this Setting exists?

Conceptually:

Debug Session ↓ Observation ↓ Evidence ↓ System Component

Evidence may contain:

source Observation
Component
strength
note
timestamp
Evidence strength currently uses:

weak
moderate
strong
Longer-term evidence evaluation may consider:

repeated observations
independent contexts
contradictory evidence
experiment results
recency
evidence strength
12. Confidence
System Components may have confidence values such as:

Low
Medium
High
The system may recommend confidence changes.

It should not silently decide what is true about the user.

Core rule:

The system recommends. The user decides.

Confidence should eventually become evidence-informed rather than relying only on raw evidence count.

13. Component Lifecycle
System Components move through a lifecycle.

Current domain states include:

Observed
Candidate
Testing
Confirmed
Adopted
Deprecated
Retired
Conceptual lifecycle:

Observed ↓ Candidate ↓ Gather Evidence ↓ Testing ↓ Experiment ↓ Confirmed / Adopted ↓ Modified / Deprecated / Retired

Not every Component must follow exactly the same path.

Lifecycle changes should be explicit.

14. Relationships
System Components can be related to one another.

Relationship types include:

triggers
requires
supports
conflicts with
protects against
amplifies
reduces
compensates for
replaced by
Example:

Ambiguous Expectations ↓ triggers Need for Clarity ↓ amplifies Information Seeking ↓ contributes to Decision Delay

The MVP does not require a graphical relationship map.

Relationship CRUD and useful relational views should come first.

15. Analysis Lenses
Personal OS provides multiple ways to investigate the same experience.

These are different analytical lenses over the same underlying Personal OS.

They are not separate applications.

16. Systems Lens
The Systems Lens asks questions such as:

What Setting might be operating?
What Rule could be driving this?
What Assumption supports that Rule?
Under what conditions does this happen?
What changed the outcome?
Example:

Situation → Unexpected requirement change

Assumption → "I should understand the entire problem before acting."

Rule → "Do not proceed until requirements are clear."

Setting → Need for Clarity

The Systems Lens emphasizes behavioral mechanics rather than judgment.

17. Protective Lens
The Protective Lens asks a different set of questions:

What seemed important?
What felt threatened or unavailable?
What did the response attempt to accomplish?
What Need might have been involved?
What Protective Strategy appeared?
Does this strategy still help in the current situation?
What does the strategy cost?
Example:

Situation → Requirements became unpredictable

Need → Predictability

Protective Strategy → Delay commitment until uncertainty decreases

Setting → Need for Clarity

The Protective Lens must remain nondiagnostic.

Personal OS must not claim:

"You do this because of trauma."

It may instead ask:

"Could this response have been attempting to create predictability, safety, control, connection, or another important condition?"

"Not sure" must remain a valid answer.

18. Hybrid Analysis
Users may eventually analyze something through:

Systems Lens
Protective Lens
Both
Both lenses feed the same knowledge model.

Example:

SYSTEMS

Rule: Get complete information before acting.

Assumption: Incomplete information creates unacceptable risk.

PROTECTIVE

Need: Predictability.

Protective Strategy: Delay action until uncertainty decreases.

SHARED SYSTEM COMPONENT

Need for Clarity

This shared model is an important architectural principle.

19. Existing Component Detection
Repeated discoveries should strengthen existing knowledge rather than automatically create duplicates.

Example:

Existing Component:

Need for Clarity Evidence Count: 3

New Debug Session identifies:

Need for Clarity

The application should offer:

[ Add Evidence to Existing Component ]

or:

[ Create Separate Component ]

Preferred result:

Need for Clarity Evidence Count: 4

Avoid creating:

Need for Clarity Need for Clarity Need for Clarity Need for Clarity

Duplicate prevention is important because the System should become clearer, not noisier, over time.

20. Experiments
Personal OS should not stop at insight.

Users should be able to test hypotheses.

Experiment structure:

Title
Related Component
Hypothesis
Variable or Change
Success Criteria
Start Date
End Date
Status
Observations
Conclusion
Possible statuses:

Draft
Active
Completed
Abandoned
Possible conclusions:

Supported
Mixed
Not Supported
Inconclusive
Example:

Setting:

Need for Clarity

Hypothesis:

I do not need complete certainty to make good decisions.

Test:

Before making a decision, explicitly define the minimum information required.

Success Criteria:

Make the decision without reopening information gathering unless new material information appears.

Result:

Supported.

Experiments convert:

"I think this might be true."

into:

"I tested this."

21. Experiment Loop
The desired Experiment lifecycle is:

System Component ↓ Identify Question ↓ Create Hypothesis ↓ Design Experiment ↓ Run Experiment ↓ Capture Observations ↓ Evaluate Outcome ↓ Update Component ↓ Candidate Release Change

Experiments should eventually influence confidence and release decisions.

22. Operating Conditions
The system should help users understand the conditions under which they operate well or poorly.

Primary categories:

Known Good Conditions
Conditions correlated with effective operation.

Performance Degradation Factors
Conditions associated with reduced performance.

Resource Requirements
Resources required for effective operation.

Warning Signs
Indicators that the system may be degrading.

Recovery Methods
Actions known to help restore operation.

Example:

Known Good Condition: Clear decision ownership

Performance Degradation: Repeated context switching

Warning Sign: Excessive information gathering

Recovery Method: Reduce active commitments

23. Weekly Review
Weekly Review should be data-driven.

It should not simply be another blank reflection form.

The application should assemble relevant information from the system.

Example:

WEEKLY SYSTEM REVIEW

Period: October 5 - October 11

Debug Sessions: 4

New Candidate Components: 2

Existing Components Gaining Evidence: 3

Experiments Completed: 1

Possible Changes: 2

User workflow:

Review observations → Review component changes → Review experiments → Confirm/reject findings → Add version notes → Optionally create Release

The application should help users review what already happened rather than requiring them to reconstruct the week from memory.

24. Version Tracking
Version tracking is a signature Personal OS feature.

Personal development is represented as explicit changes to the user's operating model.

Example:

PERSONAL OS v1.2

MODIFIED

Old Rule:

Always finish what you start.

New Rule:

Finish work that remains valuable.

Reason:

Repeated completion of low-value commitments created unnecessary workload.

Evidence:

DBG-0031 REV-0018 EXP-0008

Result:

Reduced unnecessary workload.

25. Releases
A Release represents a meaningful snapshot or change to the Personal Operating System.

A Release may contain:

version number
title
summary
release date
changes
Release changes may include:

Added
Modified
Adopted
Deprecated
Retired
Restored
Release changes should capture:

Versioning must represent actual system changes.

It must not become a disguised journal.

26. Version Number Philosophy
The product may support software-inspired versioning.

Examples:

Major:

2.0

Large shift in how the Personal OS operates.

Minor:

2.3

Meaningful new Setting, Rule, or operating practice.

Patch:

2.3.1

Small refinement.

Strict semantic-version rules should not be forced unless users find them useful.

The metaphor should clarify progress, not create administrative overhead.

33. Tags
Tags provide flexible user-defined organization.

They should supplement, not replace, the structured Component type and category model.

Examples:

work decision-making communication planning energy uncertainty

Avoid requiring excessive tagging.

34. History
History provides access to prior Debug Sessions.

Users should be able to:

view active history
inspect sessions
archive sessions
view archived sessions
restore archived sessions
permanently delete sessions
Permanent deletion should explain its downstream impact.

Example:

Deleting this Debug Session removes:

the Debug Session
derived Observations
Evidence relationships from those Observations
System Components may remain if they have independent existence/evidence.

35. Data Ownership
Personal OS should communicate:

Your Personal OS belongs to you.

Users should have:

export access
archive controls
deletion controls
complete account deletion
Potential export formats:

JSON Markdown CSV PDF

JSON should be the canonical full-data export.

36. Privacy
Personal OS may contain extremely personal information.

Privacy is therefore part of product design, not merely infrastructure.

Principles:

Private by default.
User-owned data.
No behavioral-data advertising model.
Real deletion controls.
Exportability.
Least-privilege database access.
Row Level Security.
Sensitive reflection content excluded from technical logs.
AI processing should be explicit and optional.
Shared/professional functionality must use explicit user-controlled access.

Allowed diagnostic information may include:

This boundary must be maintained when diagnostics are extended.

38. AI Philosophy
AI is not required for the core product.

The structured system must remain useful without AI.

Potential future AI assistance includes:

identifying recurring candidate Components
suggesting relationships
suggesting possible Rules or Assumptions
proposing Experiments
summarizing Weekly Reviews
generating draft Release notes
identifying contradictory evidence
summarizing changes between Releases
Core rule:

AI suggests. The user decides.

AI should not present speculative psychological conclusions as facts.

Example:

Good:

"Three recent Debug Sessions mention unclear expectations. Would you like to review these as possible evidence for Need for Clarity?"

Bad:

"You have a psychological need for control."

39. User Experience Principles
39.1 Structured Before Unstructured
Use structured workflows where the structure improves learning.

Do not turn everything into free-form text.

39.2 Progressive Disclosure
Do not show users the entire System model during first use.

Reveal complexity as needed.

39.3 Human Authority
The application can suggest:

Components
relationships
confidence changes
experiments
The user approves meaningful conclusions.

39.4 Evidence Over Assertion
Whenever possible, claims about the user's operating system should point back to observations.

39.5 Useful, Not Addictive
Avoid:

guilt-inducing streaks
artificial engagement loops
gamifying disclosure
meaningless badges
forced daily check-ins
The product should be useful when needed.

39.6 Nonjudgmental Language
The product investigates behavior.

It does not label users as broken.

Prefer:

"Current configuration"

"Candidate Setting"

"Protective Strategy"

"Performance Degradation"

Avoid:

"Defect"

"Faulty personality"

"Broken behavior"

44. Application Architecture Principles
Server-First Data Access
Prefer server-side authenticated database operations where practical.

Client code should be introduced when interactive behavior requires it.

Validation
All meaningful external/user inputs should be validated.

Zod is the current application validation library.

Database constraints remain the second line of defense.

Authorization
Authorization should not depend solely on UI logic.

Database RLS is required for user-owned Personal OS data.

Domain Logic
Domain rules should be isolated from presentation code where practical.

Examples:

component lifecycle confidence recommendation release-generation logic experiment conclusions

Prefer:

lib/domain/

over embedding domain rules inside page components.

46. Database Design Principles
Relational First
The domain contains meaningful relationships.

Use relational modeling instead of reducing system knowledge to JSON documents.

Provenance
Important knowledge should be traceable to its source.

Example:

Setting → Evidence → Observation → Debug Session

Soft Removal Where Useful
Archive user inputs when useful.

Support explicit permanent deletion separately.

Explicit Change Records
Version history should store meaningful before/after changes rather than trying to reconstruct them later from updated rows alone.

48. Error Handling
User-facing failures should be safe and understandable.

Do not expose raw database details.

Technical details may be sent to sanitized diagnostics where appropriate.

Preferred pattern:

User: "Unable to save this Debug Session."

Diagnostics: code technical area safe error metadata

Never include reflection contents in logs.

59. Architecture Decision Principles
Before changing core architecture, ask:

Does the change improve the primary product loop?
Does it preserve evidence provenance?
Does it preserve user control?
Does it protect sensitive data?
Does it reduce or increase unnecessary complexity?
Can it be implemented incrementally?

Personal OS does not digitize introspection.
